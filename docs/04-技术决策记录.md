# 04 · 技术决策记录(ADR)

记录本项目的不可逆技术决策:当时考虑过什么、为什么这样选、留下了什么已知限制。新人读这页可以避免重新踩一遍已经踩过的坑。格式:背景 → 决策 → 被否方案 → 后果。

---

## ADR-001 画布缩放用 CSS `zoom` 而非 `transform: scale()`

**背景**:编辑器画布需要 40%–100% 缩放,拖拽落点计算依赖"鼠标坐标与元素矩形同一坐标系"。

**决策**:画布容器用 CSS `zoom` 属性缩放(`CanvasArea.vue` 的 `.phone-frame`)。`zoom` 参与布局,`getBoundingClientRect()` 返回的即是屏幕坐标,与 `DragEvent.clientY` 天然同系,落点计算(`drop-target.ts`)无需任何坐标换算。

**被否方案**:`transform: scale()` 不参与布局,矩形仍是未缩放尺寸,所有命中/落点计算都要手动乘缩放系数,且缩放不改变占位高度会引入滚动错位。

**后果与依据**:
- 兼容性(来源:MDN,2026-10 核查):`zoom` 已标准化(CSS Viewport Module L1),Baseline 2024 —— Chrome 1+/Edge 12+/Safari 4+(现代版本行为与标准一致)/**Firefox 126**(2024-05)起可用。项目 `engines` 只约束 Node;浏览器侧按 Baseline 2024 假设。
- 已知限制:Safari 早期版本对 zoom 有非标准差异;如需支持旧 Safari,需回归测试画布拖拽。

## ADR-002 数据层用 localStorage,而非 IndexedDB 或后端

**背景**:MVP 无后端,数据(页面 Schema、模板、剪贴板)需要持久化。

**决策**:统一 localStorage,键集中在 `shared/constants.ts` 的 `STORAGE_KEYS`,读写收敛在 `stores/` 各 store,容错统一走 `shared/utils/storage.ts`。

**被否方案**:
- IndexedDB:容量大、支持 Blob,但 API 异步复杂、调试不便,对 MVP 规模(个位数页面)是过度设计。
- 后端:由 edit-visio-console(Spring Cloud)承担,属下一阶段;`stores/pages.ts` 的注释保留了替换点。

**后果与依据(实测,2026-10,见 `src/stores/__tests__/history-cost.spec.ts`)**:
- 单页带 4 张 300KB dataURL 图片时,页面 JSON ≈ **1172KB**;约 4-5 个这样的页面就会逼近 5MB 配额。
- 缓解:上传图片 Canvas 压缩(750px/0.82);首页存储用量条(`usageBytes`/`STORAGE_QUOTA`)可视化风险;写入失败经 `persistError` 显式提示。
- 已知限制:真正的图片应走图床或 IndexedDB,**这是配额问题的根因**,后端阶段优先解决。

## ADR-003 撤销系统用全量快照,而非操作流(inverse patches)

**背景**:编辑器需要撤销/重做/时间线跳转(`jumpTo`/`jumpForward`),操作类型十余种且持续增加。

**决策**:每次变更前 `pushHistory` 存整页快照(`{label, snapshot}`),撤销即恢复快照。上限 50 步;`prop:`/`page:` 类连续输入 600ms 内合并为一步。

**被否方案**:操作流(记录 add/remove/move 的逆操作)内存省、可做协作,但每种新操作都要正确实现正/逆两个函数,漏一个就产生不可撤销的脏状态;对 MVP 是高风险复杂度。

**后果与依据(实测 2026-10)**:
- 正确性:属性测试(`editor-properties.spec.ts`,fast-check)对随机操作序列验证:I1 undo 全部精确还原初始、I2 redo 全部还原最终、I3 jumpTo(0) ≡ 逐次 undo、I4 move 保持多重集与相对顺序、I5 历史不超上限。
- 成本:带图页面单快照 ≈1.2MB,**历史满载时堆内存足迹 ≈54MB**(4×300KB 图 × 50 步);推进 50 步纯计算耗时 ≈193ms,可接受。
- 已知限制:大图页面的内存足迹是真实代价;缓解方向(优先级递增时再做):快照共享不可变结构、dataURL 存 IndexedDB 引用、或迁移到操作流。

## ADR-004 拖拽用 HTML5 Drag & Drop,而非 Pointer Events 自实现

**背景**:物料入画布、画布内排序、图层面板排序都需要拖拽。

**决策**:原生 HTML5 DnD(`draggable` + dragstart/dragover/drop),配合视口边缘自动滚动。

**被否方案**:Pointer Events 自实现拖拽——可控性强、支持触屏,但需自己处理命中测试、自动滚动、拖拽影像,复杂度高;HTML5 DnD 开箱即用且桌面体验成熟。

**后果与已知限制**:
- **触屏设备上编辑器拖拽不可用**:HTML5 DnD 规范(W3C)基于鼠标/笔交互模型,移动浏览器不从触摸手势派发 dragstart 等事件。因此**编辑器定位桌面浏览器,移动端仅作为预览面**(`/preview/:id` 随浏览器正常滚动)——这是有意的产品边界,不是缺陷。
- 若未来需要平板编辑,替换点是统一的:DragPayload 状态机(`editor.store` 的 dragging)已与事件解耦,改造成本集中在组件层事件绑定。

## ADR-005 Schema 演进用"可选字段 + 加载侧过滤",而非版本迁移器

**背景**:页面 Schema(`shared/types.ts`)会持续加字段(如 `hidden?`),localStorage 里的旧数据必须永远能打开。

**决策**:新字段一律可选(向后兼容);加载时逐条校验(`isValidRecord` 等),非法条目直接过滤;存储解析失败备份原始数据(限量 3 份)后降级为空。**禁止**在加载路径做破坏性迁移。

**被否方案**:版本号 + 迁移函数链(schemaVersion 字段已预留 `SCHEMA_VERSION`)——在出现"必须改写旧字段语义"的需求前,迁移器是多余的复杂度。

**后果**:加字段的心智负担 = "可选 + 默认行为与缺省一致";校验函数即文档(`isValidRecord`/`isValidComponentTemplate`/`isValidPageTemplate`,备份导入复用同一份真相)。
